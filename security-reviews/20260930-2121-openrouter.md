# Security review (openrouter worktree, 2026-09-30)

## Summary

This repository is a small, dependency-free tool: a Node orchestrator (`scripts/security-review.mjs`)
that runs LLM security-review agents (Claude Code, Codex, and an OpenRouter model behind Claude Code)
each in its own git worktree against an untrusted repository, then publishes their fixes as PRs and
their findings as SARIF, plus two GitHub workflows, two local runner wrappers, one stream-log
summariser with tests, and a superseded legacy shell script under `extras/`. The code quality is
good: no shell interpolation anywhere (all subprocess calls are `execFileSync`/`spawn` without a
shell), no secrets committed, an explicit "no keys in this repo" guard, and a stream summariser
that carefully keeps model output and file contents out of public job logs. The weaknesses found
all sit on the trust boundary the tool deliberately creates — an LLM agent reading attacker-
influenced repository content inside a CI job that holds a write-capable GitHub token and provider
API keys: the Claude agent was not fenced to its edit-only toolset the way the OpenRouter agent is
(fixed), the job's `GITHUB_TOKEN` is persisted in `.git/config` where the Codex agent can read it
(script side fixed, workflow side reported), several third-party actions are pinned by mutable
tags, the tool script itself is fetched from a caller-chosen ref defaulting to `main`, the agent
CLI is installed unpinned at its latest release, and the legacy `extras/` script had the same
missing tool fence (fixed) and still runs Codex with `--full-auto` (left, superseded). No secrets,
injection, path traversal, SSRF, unsafe deserialization or crypto issues were found in the
JavaScript itself.

### SR-01 — Claude agent not fenced to its edit-only toolset (Fixed)

`--allowedTools Read,Edit,Write,Glob,Grep` only pre-approves those tools; every other Claude Code
tool (Bash, the Agent/Task sub-agent fan-out, WebFetch, …) stayed *available* to the model. The
OpenRouter agent definition already carries `--tools Read,Edit,Write,Glob,Grep` with a comment
explaining that the model actively reached for `Agent` and `Bash` — the same gap existed for the
plain `claude` agent.

**Impact:** the agent reads untrusted repository content, so a prompt-injected file can steer it
toward tools it was never meant to have. In headless `acceptEdits` mode the extra tools are
denied per call, but that is a per-call refusal rather than a fence: it depends on Claude Code's
permission defaults holding, and each attempt burns turns (and, via sub-agents, in-flight
requests) while the child process holds `GH_TOKEN`, `ANTHROPIC_API_KEY` and a worktree whose
shared git config contains the job token (see SR-03).

**Fix:** added `"--tools", "Read,Edit,Write,Glob,Grep"` to the `claude` agent's args
(`scripts/security-review.mjs:122`), the same fence the `openrouter` agent already has. The
five allowed tools are unchanged, so existing behaviour (edits only, no shell, no tests) is
preserved — the fence only removes tools that were never intended to be used.

### SR-02 — Third-party actions pinned by mutable tags (Not fixed, workflow file)

`actions/checkout@v4` (lines 163 and 168), `actions/setup-node@v4` (176),
`github/codeql-action/upload-sarif@v4` (263) and `actions/upload-artifact@v4` (272) are pinned by
version tags, which are mutable references. `openai/codex-action` is correctly pinned to a full
commit SHA (line 203).

**Impact:** the `review` job runs with `contents: write`, `pull-requests: write` and
`security-events: write` on the *calling* repository, and its environment carries the provider
API secrets. Anyone who can move those tags (a compromised action repo, a forced re-push) runs
arbitrary code with that authority in every repository using this workflow.

**Fix I would make:** pin each action to a full 40-character commit SHA, e.g.
`uses: actions/checkout@<sha> # v4.2.2`, `actions/setup-node@<sha> # v4.4.0`,
`github/codeql-action/upload-sarif@<sha> # v4`, `actions/upload-artifact@<sha> # v4.6.2`
(updating the trailing comment on each bump so the intended version stays reviewable). This is
in `.github/workflows/security-review.yml`, which this review is not allowed to modify.

### SR-03 — Job token persisted in `.git/config` where an agent can read it (Partially fixed)

`actions/checkout` (step "Check out repo under review", line 162) persists the job's
`GITHUB_TOKEN` (`contents: write`, `pull-requests: write`) as an `http…extraheader` in the main
checkout's `.git/config`. Both agent worktrees created later (`git worktree add` from that
checkout, and the Codex worktree at `$RUNNER_TEMP/codex-wt` prepared by the workflow) share that
same git directory. The Codex agent runs with the `:workspace` sandbox and reviews untrusted
content, so injected instructions can direct it to simply read `$GITHUB_WORKSPACE/.git/config`
and exfiltrate or use a repo-write token. The Claude agents are fenced to file tools inside their
worktree, but with SR-01 unfixed they could have reached for the same file.

**Impact:** escalation from "model reads repository content" to "attacker holds a token that can
push arbitrary commits to the repository under review".

**Fixed here (script side):** `scripts/security-review.mjs` no longer depends on the persisted
credential for its own network operations — `git fetch origin` and `git push` now carry the token
from the `GH_TOKEN` environment variable as a per-command `-c http.https://github.com/.extraheader`
value (new `gitAuthArgs()` helper), which is exactly the header `actions/checkout` would persist.
This keeps CI behaviour identical and makes the workflow-side fix possible without breaking the
push.

**Fix still needed (workflow file, not allowed in this run):** add `persist-credentials: false`
to the "Check out repo under review" step (line 162), and give the `git fetch` in the
"Prepare Codex worktree" step (line 196) the same per-command header, e.g.
`git -c http.https://github.com/.extraheader="AUTHORIZATION: basic $(printf 'x-access-token:%s' "$GH_TOKEN" | base64)" fetch --quiet origin`
with `GH_TOKEN: ${{ github.token }}` in that step's env. The "Check out security-review tool"
step already sets `persist-credentials: false` (line 174).

### SR-04 — Agent CLI installed unpinned at latest (Not fixed, workflow file)

The "Install … CLI" step (line 180) runs `npm install -g @anthropic-ai/claude-code` with no
version, so every run pulls whatever release is current.

**Impact:** a compromised or yanked-then-republished npm release becomes code that runs with the
job's secrets in its environment; runs are also not reproducible.

**Fix I would make:** install a pinned version (`npm install -g @anthropic-ai/claude-code@<version>`)
and bump it deliberately, the same way `openai/codex-action` is pinned. This is in
`.github/workflows/security-review.yml`, which this review is not allowed to modify.

### SR-05 — Tool script fetched from a caller-chosen ref defaulting to `main` (Not fixed, workflow file)

The `tool-repository` / `tool-ref` inputs (lines 97-104, used at 170-171) decide what code the
`review` job executes, and `tool-ref` defaults to `main`. Whoever can call the workflow chooses
that ref (they are the repository owner, so this is not a privilege *escalation*), but the default
means any compromise of this repository's `main` branch propagates to every caller's repository
with their write token.

**Impact:** the tool repository is a supply-chain root for all callers; the mutable default widens
the blast radius of a compromise of it.

**Fix I would make:** default `tool-ref` to a pinned release tag that matches the release on the
`uses:` line (as the README already instructs callers to do), so a caller accepting the defaults
gets reviewed, immutable code. This is in `.github/workflows/security-review.yml`, which this
review is not allowed to modify.

### SR-06 — Legacy `extras/security-review.sh` (Partially fixed)

The superseded reference script had the same `--allowedTools`-only gap as SR-01 on its claude
invocation (lines 82-86), and still runs Codex with `--full-auto` (full command execution; the flag
was removed in codex-cli 0.15x, so the line is already broken against current CLIs) and Gemini
with `--approval-mode auto_edit` (lines 87-92).

**Impact:** only if someone copies the file out of `extras/` and uses it — nothing in this repo
executes it. The claude gap is the same as SR-01; `--full-auto` additionally grants command
execution inside the reviewed repository.

**Fixed here:** added `--tools "Read,Edit,Write,Glob,Grep"` to the claude invocation
(`extras/security-review.sh:85`).

**Left as-is:** the codex and gemini branches, because the file is documented as superseded and
kept for reference only; the correct action for those is deleting the file or its codex/gemini
branches rather than half-fixing a legacy path, which is beyond a minimal focused change. Noted
here so the owner can decide.
