# Security review — multi-llm-security-review

## Summary

This repository is a CI/CD orchestrator: a reusable GitHub Actions workflow plus a Node script that
launches third-party coding agents (Claude Code, Codex, an OpenRouter-backed Claude Code) against a
repository, then commits, pushes and opens a pull request with whatever those agents wrote. It has
no runtime dependencies, no network server, no database and no user-facing parsing, so the classic
injection/authz/crypto classes largely do not apply. The real attack surface is the trust boundary
between the *agent process* (which is driven by a large language model reading untrusted repository
content) and the *publishing machinery* (which holds a repo-write token and provider API keys, and
publishes to a possibly public pull request). The most serious issue found is that the script
followed the agent-written `.security-review.md` and `.security-review.sarif` paths with
`statSync`/`existsSync`, so an agent with a shell (the Codex sandbox has one) could leave a symlink
there and have an arbitrary file from outside the worktree read into the public PR body — fixed by
`lstat`-ing and requiring a regular file. Also fixed: every agent subprocess inherited `GH_TOKEN`
and all three provider API keys regardless of which agent it was; `where.exe` resolved agent
binaries from the current directory first on Windows; and `AGENT_DEFS[agent]` resolved through
`Object.prototype`. The remaining findings are workflow-file issues (unpinned CLI install, the
checkout token persisted on disk while agents run, no explicit `permissions:` block) which I was
instructed not to edit, and accepted-by-design properties (prompt injection steering an
auto-pushed PR, public PRs and log artifacts disclosing unfixed findings) which the README already
documents.

### SR-01 — High — Symlinked report or SARIF discloses an arbitrary file into the published PR body

**File:** `scripts/security-review.mjs:341` (report), `scripts/security-review.mjs:254` (SARIF)
**CWE-59** (link following) leading to **CWE-200** (information exposure).

**Description.** After the agent finished, the script did:

```js
if (!existsSync(report) || statSync(report).size === 0) { … }
…
renameSync(report, join(wt, committedReport));
…
const reportText = readFileSync(join(wt, committedReport), "utf8");
```

`existsSync` and `statSync` both follow symbolic links, and `renameSync` moves the *link*, not the
target. If `.security-review.md` in the worktree is a symlink, the size check passes against the
target, the link is renamed into `security-reviews/`, and `readFileSync` then reads the **target**
and writes up to 60 000 characters of it into the pull-request body. The SARIF path had the same
shape (`existsSync` + `readFileSync`), landing the target's contents in the uploaded SARIF artifact.

This is reachable. The Codex agent runs under `permission-profile: ":workspace"` with a real shell,
so a single `ln -s` in its workspace is enough; the agent is steered by a model reading repository
content it did not write (see SR-06). Plausible targets on a GitHub runner include the checkout's
`.git/config` — which holds the `GITHUB_TOKEN` as an `http.extraheader` (SR-03) — `~/.npmrc`,
`~/.gitconfig`, or the other agents' log files.

**Impact.** Arbitrary file read from the runner, published to a pull request that is world-readable
on a public repository (and to the code-scanning SARIF). If the file read is the checkout's
`.git/config`, the repository's `contents: write` / `pull-requests: write` token is disclosed.

**What I changed.** Both call sites now `lstat` and require a regular file:

- `exportSarif` uses `lstatSync(src, { throwIfNoEntry: false })`; a non-regular entry is logged,
  removed and skipped instead of read.
- `runAgent` uses `lstatSync(report, { throwIfNoEntry: false })` and throws a distinct error if the
  entry exists but is not a regular file, before the `rename`/`readFileSync`. Behaviour for a normal
  regular-file report is byte-for-byte unchanged: same missing/empty error message, same flow.

`statSync` is no longer imported.

### SR-02 — Medium — Agent subprocess inherits the push token and every provider API key

**File:** `scripts/security-review.mjs:216` (`spawn … env`), helper added at `:173-185`
**CWE-522** (insufficiently protected credentials) / **CWE-200**.

**Description.** `runCli` spawned the agent CLI with `env: { ...env, ...extraEnv }` — the script's
entire environment. That environment contains, at minimum:

- `GH_TOKEN` (the workflow passes `${{ github.token }}`), which can push branches and open PRs;
- whichever of `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY` are set. In CI the
  workflow already narrows these per matrix job, but **the documented local path does not**:
  `scripts/run-local.sh` defaults `AGENTS="claude openrouter"` and loads all three keys from `.env`,
  so the Claude process received the OpenRouter key and vice versa.

The agent is an LLM acting on untrusted repository content. It is not required to have a shell to
leak these — several tools in an agent CLI surface environment values, and the agent's own log file
is uploaded as a workflow artifact. Least privilege says the Claude process has no business holding
the OpenAI key or a token that can write to the repository.

**Impact.** Cross-provider key exposure, and exposure of a repo-write token, to a process driven by
untrusted input. Widens SR-06 from "arbitrary file content in a PR" to "credential theft".

**What I changed.** Added an `agentEnv(def)` helper that builds the child environment by deleting
every provider key except `def.key`, and deleting `GH_TOKEN` / `GITHUB_TOKEN` /
`GH_ENTERPRISE_TOKEN` / `GITHUB_ENTERPRISE_TOKEN`, then layering the agent's own `extraEnv` on top.
`runCli`'s `extraEnv` option became `childEnv`, and `runAgent` passes `agentEnv(def)`. Nothing else
changes: `git` and `gh` are invoked by the *parent* through `execFileSync`, which still inherits the
full `process.env`, so pushing and PR creation are unaffected. The `openrouter` agent's deliberate
`ANTHROPIC_API_KEY: ""` still wins, because `extraEnv` is merged last.

### SR-03 — Medium — The checkout token stays in `.git/config` while the agents run

**File:** `.github/workflows/security-review.yml:162-165`
**Status: Not fixed (workflow file).** **CWE-522.**

**Description.** `Check out repo under review` uses `actions/checkout@v4` without
`persist-credentials: false` (the tool checkout at line 167 does set it). Checkout therefore writes
`http.https://github.com/.extraheader = AUTHORIZATION: basic <base64 of x-access-token:GITHUB_TOKEN>`
into the workspace's `.git/config`. Every agent worktree is a `git worktree` of that same checkout,
so the file is a few directory levels above the agent's working directory and is readable for the
whole duration of the review — by the Codex shell directly, or by an absolute-path `Read` from the
Claude Code agents.

The credential cannot simply be dropped: `scripts/security-review.mjs` relies on it for
`git push -u origin <branch>`.

**Impact.** A prompt injection (SR-06) or a symlink (SR-01, now fixed) can recover a token with
`contents: write` and `pull-requests: write` on the calling repository and copy it into a public PR,
a log artifact or a committed file.

**Exact fix I would make.** Set `persist-credentials: false` on the first checkout too, and give the
push its credential only at push time, never on disk:

```yaml
      - name: Check out repo under review
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
          persist-credentials: false
```

and in `scripts/security-review.mjs`, replace the bare `git("push", …)` with a per-invocation
header (the parent process keeps `GH_TOKEN`; the agent's environment no longer has it after SR-02):

```js
const pushArgs = env.GH_TOKEN
  ? ["-c", `http.https://github.com/.extraheader=AUTHORIZATION: basic ${Buffer.from(`x-access-token:${env.GH_TOKEN}`).toString("base64")}`]
  : [];
git(...pushArgs, "push", "--quiet", "-u", "origin", branch);
```

I did not make the script-side half of this change either, because on its own — without the
workflow change — it would be dead code, and with `persist-credentials` still true it would not
reduce any exposure. The two must land together.

### SR-04 — Medium — Unpinned global CLI install runs with secrets in the job

**File:** `.github/workflows/security-review.yml:180-185`
**Status: Not fixed (workflow file).** **CWE-1357 / CWE-829** (reliance on an un-vetted component).

**Description.** `npm install -g @anthropic-ai/claude-code` resolves to whatever the `latest` dist-tag
points at when the job runs, with no version range, no lockfile and no `--ignore-scripts`. The
package's install scripts and its entire transitive tree execute in a job that holds
`ANTHROPIC_API_KEY`/`OPENROUTER_API_KEY`, `GITHUB_TOKEN` with write scopes, and the source of the
repository under review. A compromised release — or any compromised transitive dependency — is
immediate code execution with those credentials. Every run also silently changes what code is
executed, which is at odds with the care taken to pin `openai/codex-action` by SHA at line 203 and
to expose a `tool-ref` input for pinning this repo's own script.

**Impact.** Supply-chain compromise of every calling repository at once, with repo-write credentials.

**Exact fix I would make.** Add a pinned version input and use it, so callers can pin a release and
review upgrades:

```yaml
      claude-cli-version:
        description: "Version of @anthropic-ai/claude-code to install (exact version, not a range)"
        type: string
        default: "2.0.1"   # bump deliberately
```

```yaml
      - name: Install ${{ matrix.agent }} CLI
        env:
          AGENT: ${{ matrix.agent }}
          CLI_VERSION: ${{ inputs.claude-cli-version }}
        run: |
          case "$AGENT" in
            claude|openrouter) npm install -g "@anthropic-ai/claude-code@$CLI_VERSION" ;;
            codex)  ;; # installed by openai/codex-action
          esac
```

(This snippet also carries the SR-07a fix.)

### SR-05 — Medium — The reusable workflow declares no `permissions:`

**File:** `.github/workflows/security-review.yml:113-160`
**Status: Not fixed (workflow file).** **CWE-250** (execution with unnecessary privileges).

**Description.** Neither the workflow nor either job sets `permissions:`. A `workflow_call` workflow
inherits the caller job's `GITHUB_TOKEN` scopes, and `examples/caller.yml` grants
`contents: write`, `pull-requests: write`, `security-events: write` and `actions: read`. So the
`plan` job — which only reads three booleans and writes a job output, and needs **no** token at all
— runs with a write token, as does every step of `review`, including `npm install -g` (SR-04) and
the agent processes themselves. `extras/single-repo-workflow.yml` does declare workflow-level
permissions; the reusable one does not. `no-secrets.yml` correctly uses `permissions: {}`.

**Impact.** Any code executed anywhere in these jobs — a compromised CLI release, a compromised
action, an injected step — gets the full set of write scopes rather than the minimum.

**Exact fix I would make.** Add explicit least-privilege blocks:

```yaml
jobs:
  plan:
    runs-on: ubuntu-latest
    permissions: {}
    …
  review:
    needs: plan
    runs-on: ubuntu-latest
    permissions:
      contents: write        # push the review branch
      pull-requests: write   # gh pr create
      security-events: write # upload-sarif
      actions: read          # upload-sarif on private repos
    …
```

Callers already grant exactly these, so this narrows rather than requires anything new. Note that
`permissions` cannot be made conditional on `inputs.upload-sarif`, so `security-events: write` has
to be declared unconditionally here; callers that leave `upload-sarif` off can simply not grant it
(the step is skipped anyway).

### SR-06 — Medium — Prompt injection in the reviewed repository reaches an auto-pushed PR

**File:** `scripts/security-review.mjs:370-375` (`git add -A`, `git commit`, `git push`)
**Status: Not fixed (inherent to the design; mitigated and documented).** **CWE-94-adjacent /
LLM01 prompt injection.**

**Description.** The agent reads the repository under review, including files whose only purpose may
be to address the agent (`AGENTS.md`, `CLAUDE.md`, `README`, comments in any source file). It then
writes files with `Write`/`Edit` in a worktree that the script commits **wholesale**
(`git add -A`) and pushes without any human in the loop. Injected instructions in repository content
can therefore cause arbitrary file contents to be committed to a branch of the repository and
proposed as a "security fix". This is the defining risk of the whole tool, not a slip; I am
recording it so it appears in the SARIF and so the mitigations are explicit.

**Impact.** A malicious contribution merged into the reviewed repo (or an untrusted repo passed to
the local runner) can get arbitrary changes into a plausible-looking, automatically opened PR, and —
before SR-01/SR-02 were fixed — could exfiltrate credentials through it.

**Why I left it, and what already limits it.**

- Everything lands on a **separate branch** as a **draft PR** (`DRAFT` defaults to `1`), never on
  the base branch; a human reviews before merge.
- The token used cannot push `.github/workflows/`, and the script additionally reverts any change
  under that path (`scripts/security-review.mjs:362-369`) so an injected workflow change cannot even
  be proposed.
- PRs opened with `GITHUB_TOKEN` do not trigger further workflows, so an injected change cannot
  chain into another privileged run. The README documents this at "Caveats".
- SR-01 and SR-02 close the two credential-disclosure paths that turned this from "bad patch
  proposed" into "secrets stolen".

Removing the remaining risk would mean not auto-pushing at all, which is the product. The honest
mitigation is the one the README already states: treat the output as an untrusted patch and review
it. Worth adding to the README's Caveats explicitly: *do not point the local runner at a repository
you do not trust.*

### SR-07 — Low — GitHub expression expanded into a shell script body

**a) `.github/workflows/security-review.yml:180-185` — Not fixed (workflow file)**
**b) `extras/single-repo-workflow.yml:96-102` — Fixed**
**CWE-78** (pattern), not currently exploitable.

**Description.** `case "${{ matrix.agent }}" in` textually substitutes an expression into the shell
script *before* bash parses it. Here the value is safe: `matrix.agent` comes from the `plan` job,
which builds the JSON array from three hard-coded literals (`claude`, `codex`, `openrouter`). So
this is a latent pattern, not a live vulnerability — but it is the exact construct that becomes
command injection the moment the matrix is ever fed from an input, a repo variable or a file.

**What I changed.** In `extras/single-repo-workflow.yml` (not a protected path) the value now goes
through the environment, where it can never be shell-parsed:

```yaml
        env:
          AGENT: ${{ matrix.agent }}
        run: |
          case "$AGENT" in
```

**Exact fix for the protected file.** Identical change in
`.github/workflows/security-review.yml:180-185` — see the snippet under SR-04, which combines both.

### SR-08 — Low — `where.exe` resolves the agent binary from the current directory first

**File:** `scripts/security-review.mjs:194-202`
**CWE-426** (untrusted search path).

**Description.** `resolveBin` ran `where <bin>` / `which <bin>` with the script's inherited working
directory. `where.exe` searches the **current directory before `PATH`** by default. The documented
local workflow is `scripts/run-local.sh ../other-repo` / `.\scripts\run-local.ps1 path\to\repo`,
and a user reviewing someone else's repository will very plausibly run it from inside that
repository. A `claude.exe` or `codex.exe` committed to that repo's root would then be resolved,
spawned, and handed the provider API key.

**Impact.** Local code execution on a Windows reviewer's machine from repository content, with the
provider key in the child environment.

**What I changed.** `resolveBin` now performs the lookup from a neutral directory
(`{ cwd: tmpdir() }`) for both `where` and `which`, so only `PATH` decides. Resolution of a genuinely
installed CLI is unchanged.

### SR-09 — Low — `AGENT_DEFS[agent]` resolves through `Object.prototype`

**File:** `scripts/security-review.mjs:444-446`
**CWE-1321**-adjacent (prototype-chain lookup on an attacker-influenced key).

**Description.** `AGENTS` is split from the environment and used directly as an object key:
`const def = AGENT_DEFS[agent]; if (!def) …`. `AGENTS="constructor"` or `AGENTS="toString"` yields a
truthy inherited value, so the "unknown agent, skipping" guard is bypassed and the code proceeds with
`def.bin === undefined`. In practice the failure is contained (the `resolveBin` call throws and is
caught by the `try/catch` at the next line, and the agent is skipped), so this is a correctness/
defence-in-depth issue rather than an exploitable one — but the guard should mean what it says.

**What I changed.** The guard is now `if (!Object.hasOwn(AGENT_DEFS, agent))`, so only the three real
agent names pass. `Object.hasOwn` is available in Node 16.9+; the script already requires Node 18+.

### SR-10 — Low — Same symlink issue in the superseded bash runner

**File:** `extras/security-review.sh:107-112`
**CWE-59 / CWE-200.**

**Description.** `[[ ! -s "$REPORT_FILE" ]]` follows symlinks, `mv` moves the link, and
`head -c 60000 "$committed_report"` then reads the target into the PR body — the SR-01 chain, in the
older script. `extras/` is documented as superseded and kept for reference, but it is executable,
committed, and someone will run it.

**What I changed.** The guard now rejects anything that is not a regular file:
`if [[ -L "$REPORT_FILE" || ! -f "$REPORT_FILE" || ! -s "$REPORT_FILE" ]]`. I deliberately did not
otherwise modernise this script (it also lacks the per-agent timeout, the Coverage check, the branch
cleanup and the SR-02 environment scrubbing of `scripts/security-review.mjs`); the supported path is
`scripts/security-review.mjs`, and rewriting reference code would be the unrelated refactoring this
review is told to avoid. If `extras/` is not actually needed, deleting it is the better fix.

### SR-11 — Low — The `claude` agent is not restricted with `--tools`

**File:** `scripts/security-review.mjs:116-123` (compare `:154-165`)
**Status: Not fixed.** **CWE-272** (least privilege).

**Description.** The `openrouter` agent passes both `--allowedTools Read,Edit,Write,Glob,Grep`
**and** `--tools Read,Edit,Write,Glob,Grep`, and the comment at line 159 explains why: "`--allowedTools`
merely pre-approves; every other tool stays available". The `claude` agent passes only
`--allowedTools`. So `Bash`, `WebFetch`, `Task`/sub-agents and the rest remain *present* for the
Claude agent and are stopped only by the permission layer at call time. README's "Edits only, no
shell" describes the intended state, and the permission layer does deny those calls in headless
mode — but the guarantee rests on one mechanism instead of two.

**Impact.** Low. Defence in depth only: no known bypass, and the same code path already observes
denials working. The consequence today is wasted turns, not execution.

**Why I left it.** Adding `--tools` to the `claude` agent removes capabilities the Claude agent
currently has available (e.g. `TodoWrite`, `Task`), which is a behaviour change to the primary,
working agent — outside "minimal, focused changes that keep existing behaviour". The recommended
change, if you want the two agents to be symmetric, is to add
`"--tools", "Read,Edit,Write,Glob,Grep",` to `AGENT_DEFS.claude.args()` and re-run once to confirm
the review quality is unaffected.

### SR-12 — Low — The agent log artifact contains the full model stream

**File:** `.github/workflows/security-review.yml:270-279`
**Status: Not fixed (workflow file).** **CWE-532** (information exposure through log files).

**Description.** `Upload agent log` uploads `${{ runner.temp }}/secreview-*/*.log`, which is the
agent's complete stdout/stderr: its reasoning, tool results and file contents, and its full
description of vulnerabilities it decided *not* to fix. On a public repository, workflow artifacts
are downloadable by anyone for the 14-day retention window. This is the exact leak the
`stream-summary.mjs` sanitiser exists to prevent for the *job log* (and which it does well —
`scripts/stream-summary.mjs:33-36` emits only tool name plus path, and the test suite asserts it),
but the unsanitised stream is then published as an artifact anyway.

**Impact.** Unfixed vulnerabilities in the reviewed codebase, with file contents, disclosed publicly
for 14 days. The README's "Caveats" notes it ("so are the agent log artifacts") and recommends using
the tool on private repos, so this is a documented trade-off rather than an oversight.

**Exact fix I would make.** Upload only `review-output.txt` (which contains just the script's own
`[agent] …` lines and, with `stream-logs`, the sanitised summaries) and gate the raw agent log behind
an opt-in input, defaulting off:

```yaml
      - name: Upload agent log
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: security-review-${{ matrix.agent }}-log
          path: |
            ${{ runner.temp }}/review-output.txt
            ${{ inputs.upload-raw-agent-log && format('{0}/secreview-*/*.log', runner.temp) || '' }}
```

### SR-13 — Low — `toRepoUri` can emit a path that escapes the repository root

**File:** `scripts/security-review.mjs:274-279`
**Status: Not fixed.** **CWE-22**-adjacent.

**Description.** The SARIF is written by the model, so every `artifactLocation.uri` in it is
model-controlled. `toRepoUri` strips a `file://` prefix, URL-decodes, and makes absolute paths
relative to the worktree — but `relative()` happily returns `../../etc/passwd`, and a URI that was
*already* a relative traversal (`../../secrets.txt`) is passed through untouched. The result goes
into the SARIF uploaded to code scanning.

**Impact.** Minimal. SARIF is metadata: the URI is a label GitHub uses to attach an alert to a file,
not something that is opened or written. Code scanning rejects or fails to resolve locations outside
the analysed tree, so the effect is a dropped or mis-attached alert, not a file read or write.

**Why I left it.** The only behaviour-preserving options are to rewrite escaping paths (producing a
wrong, misleading file reference) or to drop those results (silently losing findings, the opposite of
what the tool is for). Both are worse than letting GitHub reject an unresolvable location. If you do
want a guard, the least-bad version is to keep the result but strip the traversal for display:

```js
return u.replace(/\\/g, "/").replace(/^\.\//, "").replace(/^(\.\.\/)+/, "");
```

### SR-14 — Low — GitHub-published actions pinned by mutable tag

**File:** `.github/workflows/security-review.yml:163, 168, 176, 263, 272`
**Status: Not fixed (workflow file).** **CWE-829.**

**Description.** `actions/checkout@v4`, `actions/setup-node@v4`, `github/codeql-action/upload-sarif@v4`
and `actions/upload-artifact@v4` are pinned to major-version tags, which are mutable refs that the
publisher re-points. `openai/codex-action` is correctly pinned to a full SHA at line 203, so the

Dependabot (`.github/dependabot.yml`, `package-ecosystem: github-actions`) propose bumps:

```yaml
        uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8 # v5.0.0
```

(Resolve the current SHA for each at pin time rather than copying this one.)

### SR-15 — Low — The `.env` loaders import any variable name

**Files:** `scripts/run-local.sh:58-67`, `scripts/run-local.ps1:61-69`
**Status: Not fixed.** **CWE-15** (external control of system setting).

**Description.** Both loaders accept any `NAME=value` line matching `[A-Za-z_][A-Za-z0-9_]*` and
export it, then spawn `node`, `git` and `gh`. A `.env` containing `PATH=...`, `NODE_OPTIONS=--require
./evil.js`, `GIT_SSH_COMMAND=...` or `LD_PRELOAD=...` therefore becomes code execution in those child
processes. The loaders are otherwise careful: the value is never `eval`'d, the shell version uses
`export "$k=$v"` with proper quoting, and PowerShell uses `Set-Item env:$name` — so there is no
injection *into the loader itself*, only the inherent power of the variables it sets.

**Impact.** Low, and largely a trust statement rather than a boundary crossing: `.env` lives at the
repo root, is git-ignored, and is created by the person running the script. It matters only if a
`.env` arrives from somewhere else — copied from a teammate, or committed by a repository you cloned
and then ran the script inside of.

**Why I left it.** Restricting the loader to an allowlist would contradict the documented contract
("Any other variable documented in the README (`BASE_BRANCH`, `DRAFT`, …) is passed through") and
break users. A minimal hardening, if wanted, is to refuse a short denylist before exporting:

```bash
    case "$k" in PATH|LD_PRELOAD|LD_LIBRARY_PATH|NODE_OPTIONS|GIT_SSH_COMMAND|GIT_EXTERNAL_DIFF|BASH_ENV)
      echo "refusing to set $k from $env_file" >&2; continue ;;
    esac
```

The `.gitignore` handling around this is correct: `.env` and `.env.*` are ignored with
`!.env.example` re-included, and `.env.example` contains only empty placeholders. No secret is
committed anywhere in the repository — I grepped the tree and found none.

### SR-16 — Low — Claude Code loads project settings, and therefore hooks, from the repo under review

**File:** `scripts/security-review.mjs:116-123` and `:154-165`
**Status: Not fixed.** **CWE-829** / **CWE-94**.

**Description.** The agent is launched with its working directory set to a worktree of the repository
being reviewed. Claude Code reads project-scoped configuration from that directory — `CLAUDE.md`,
`.claude/settings.json`, and any `hooks` defined there. Hooks are shell commands the CLI executes
around tool calls, which is outside the `--allowedTools` model entirely. A reviewed repository that
ships a `.claude/settings.json` with a `PreToolUse` hook could therefore get commands executed in
the review job. The same idea applies to `AGENTS.md` for Codex, though that is instructions rather
than execution (covered by SR-06).

**Impact.** Command execution in the review job from repository content. Mitigated by SR-02 (the
child no longer holds `GH_TOKEN` or other providers' keys) but not eliminated — the checkout
credential of SR-03 is still on disk, and the job can reach the network.

**Why I left it.** The correct flag depends on the Claude Code version in use, and the workflow
installs whatever is current (SR-04), so I cannot pin down a spelling that is certain to be accepted
by the version that will actually run; passing an unrecognised flag would break every review. Recent
Claude Code versions expose `--setting-sources` for exactly this. **Verify against your installed
version**, then add to both Claude-based agent definitions:

```js
      "--setting-sources", "user",   // do not load .claude/settings.json or hooks from the repo under review
```

Pinning the CLI version (SR-04) is a prerequisite for making this change safely, which is why the two
should be done together.

## Things checked and found sound

Recording these so the absence of a finding is not mistaken for an absence of review:

- **No secrets in the repository.** `.env.example` holds empty placeholders only; `.gitignore`
  correctly ignores `.env`/`.env.*` while re-including `.env.example`; `no-secrets.yml` actively
  fails the build if this repo can even *see* a provider key, which is a good control.
- **No shell interpolation of the prompt.** `scripts/security-review.mjs` uses `spawn`/`execFileSync`
  with argv arrays throughout and never `shell: true`; the header comment at `:111` shows this is
  deliberate. The Windows `.cmd`-shim workaround at `:205-209` exists precisely to avoid
  `shell: true`, and runs the shim's JS entry point under the current `node` instead.
- **The job-log sanitiser is genuinely careful.** `scripts/stream-summary.mjs` emits only tool name
  plus `file_path`/`path`/`pattern`, strips control characters (so `::error::` workflow commands
  cannot be forged), and caps length at 160; `stream-summary.test.mjs` asserts all of that,
  including that model text, tool results and the cost estimate for non-Claude models stay out.
- **Workflow-file edits are defended twice** — the prompt tells the agent not to touch
  `.github/workflows/`, and `scripts/security-review.mjs:362-369` reverts and cleans that path
  before `git add -A` regardless.
- **The SARIF is never committed** — `exportSarif` runs before `git add -A` and removes the source
  file (`:339`, `:271`).
- **Cleanup is robust.** `process.on("exit")` plus `SIGINT`/`SIGTERM` handlers remove worktrees and
  delete branches that received no commit, so a crash cannot leave a dangling branch (or a worktree
  full of agent output) behind.
- **`gh pr create` uses `--body-file`,** so model-written report text never becomes shell arguments,
  and the body is capped at 60 000 characters.
- **`JSON.parse` on the agent SARIF is wrapped** in `try/catch` and cannot deserialize objects — no
  unsafe-deserialization exposure. There is no `eval`, no `Function`, no `vm`, no `child_process`
  with a shell, and no network call anywhere in the repository.
